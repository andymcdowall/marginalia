# Decisions

Log of choices made autonomously while implementing SPEC.md, one line each: decision + reason.

- Installed Rust via `brew install rustup-init` (the `rustup` keg) + `rustup default stable` (1.98.1); it was missing from the machine and is required by SPEC.md §3.2. Symlinked `cargo`/`rustc`/etc. from `~/.rustup/toolchains/*/bin` into `/opt/homebrew/bin` because the sandboxed shell doesn't source `~/.zshrc`/`~/.zshenv` between tool calls, so PATH-based `~/.cargo/bin` shims weren't picked up.
- Spike A (PDF, §11.3) — went with the documented **fallback** (visible "Export preview" window + `window.print()`), not the primary native `NSPrintOperation` approach. Full story:
  - Built the primary approach: a hidden `WebviewWindow` loading `print.html`, `document.write()` to inject HTML, then bridging to `NSPrintOperation` via raw `objc2`/`msg_send!` (pinned `objc2`/`objc2-foundation`/`objc2-app-kit`/`objc2-web-kit` to "0.6"/"0.3" to match what Tauri 2.12 itself pulls in and avoid duplicate-version compilation; ABI-based `msg_send!` calls don't care about the version match anyway). A `define_class!`-based one-shot delegate for `runOperationModalForWindow:delegate:didRunSelector:contextInfo:` compiled cleanly on the first real attempt.
  - Dropped the JS→Rust "pdf-ready" readiness event: `document.write()` on an already-loaded page hit real WebKit quirks (a `window.onload` listener doesn't reliably re-fire; a `window.<fn>` set by a previously-imported ES module stopped being callable after the rewrite). Replaced with a fixed 400ms settle delay after `document.write` (images are already inlined as `data:` URIs per §11.2, so there's no network wait to signal for anyway).
  - Hit a real crash: `setJobDisposition:` takes an `NSString*` constant, not an integer — sent a raw `i64` (`2`) where AppKit expected a pointer, which it dereferenced, segfaulting. Fixed by using the actual `objc2_app_kit::NSPrintSaveJob` constant instead of guessing the string value.
  - After that fix, `runOperationModalForWindow:...:` ran without crashing but its delegate callback never fired within 30s, tried both a fully hidden window and one positioned off-screen-but-visible. To isolate the cause, swapped in a diagnostic: plain synchronous `-runOperation` (which spec already warns produces blank WKWebView output) — it didn't return at all within 30s either, i.e. it deadlocks, not just renders blank. This points to WKWebView's out-of-process renderer never compositing a frame for a window that isn't genuinely on-screen in this environment, a fairly fundamental blocker rather than an API-usage mistake.
  - Per SPEC.md §11.3's own permission ("use the fallback only if the primary approach still fails after two focused attempts"), switched to the fallback: `pdf_render` now opens a real visible "Export preview" `WebviewWindow`, writes the HTML into it, injects a Print… banner calling `window.print()`, and resolves once the window is showing. Verified end-to-end: opens cleanly, no crash, no hang. Removed the `objc2*` crates from Cargo.toml since nothing uses them now. Phase 6 will need to wire the actual Export dialog to this and surface the "Use Save as PDF in the print dialog" messaging (already spec'd).
