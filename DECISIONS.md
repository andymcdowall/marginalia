# Decisions

Log of choices made autonomously while implementing SPEC.md, one line each: decision + reason.

- Installed Rust via `brew install rustup-init` (the `rustup` keg) + `rustup default stable` (1.98.1); it was missing from the machine and is required by SPEC.md §3.2. Symlinked `cargo`/`rustc`/etc. from `~/.rustup/toolchains/*/bin` into `/opt/homebrew/bin` because the sandboxed shell doesn't source `~/.zshrc`/`~/.zshenv` between tool calls, so PATH-based `~/.cargo/bin` shims weren't picked up.
- Spike A (PDF, §11.3) — went with the documented **fallback** (visible "Export preview" window + `window.print()`), not the primary native `NSPrintOperation` approach. Full story:
  - Built the primary approach: a hidden `WebviewWindow` loading `print.html`, `document.write()` to inject HTML, then bridging to `NSPrintOperation` via raw `objc2`/`msg_send!` (pinned `objc2`/`objc2-foundation`/`objc2-app-kit`/`objc2-web-kit` to "0.6"/"0.3" to match what Tauri 2.12 itself pulls in and avoid duplicate-version compilation; ABI-based `msg_send!` calls don't care about the version match anyway). A `define_class!`-based one-shot delegate for `runOperationModalForWindow:delegate:didRunSelector:contextInfo:` compiled cleanly on the first real attempt.
  - Dropped the JS→Rust "pdf-ready" readiness event: `document.write()` on an already-loaded page hit real WebKit quirks (a `window.onload` listener doesn't reliably re-fire; a `window.<fn>` set by a previously-imported ES module stopped being callable after the rewrite). Replaced with a fixed 400ms settle delay after `document.write` (images are already inlined as `data:` URIs per §11.2, so there's no network wait to signal for anyway).
  - Hit a real crash: `setJobDisposition:` takes an `NSString*` constant, not an integer — sent a raw `i64` (`2`) where AppKit expected a pointer, which it dereferenced, segfaulting. Fixed by using the actual `objc2_app_kit::NSPrintSaveJob` constant instead of guessing the string value.
  - After that fix, `runOperationModalForWindow:...:` ran without crashing but its delegate callback never fired within 30s, tried both a fully hidden window and one positioned off-screen-but-visible. To isolate the cause, swapped in a diagnostic: plain synchronous `-runOperation` (which spec already warns produces blank WKWebView output) — it didn't return at all within 30s either, i.e. it deadlocks, not just renders blank. This points to WKWebView's out-of-process renderer never compositing a frame for a window that isn't genuinely on-screen in this environment, a fairly fundamental blocker rather than an API-usage mistake.
  - Per SPEC.md §11.3's own permission ("use the fallback only if the primary approach still fails after two focused attempts"), switched to the fallback: `pdf_render` now opens a real visible "Export preview" `WebviewWindow`, writes the HTML into it, injects a Print… banner calling `window.print()`, and resolves once the window is showing. Verified end-to-end: opens cleanly, no crash, no hang. Removed the `objc2*` crates from Cargo.toml since nothing uses them now. Phase 6 will need to wire the actual Export dialog to this and surface the "Use Save as PDF in the print dialog" messaging (already spec'd).
- Phase 1: `watch.rs`'s fs-change `kind` is only ever `"modify"` or `"remove"` (checked via whether the path still exists post-debounce), never `"create"`/`"rename"`. `notify-debouncer-mini` (the spec'd dependency) collapses raw create/modify events into one coarse `DebouncedEventKind` before we ever see them, so a real create/modify split isn't available without dropping the debouncer and re-implementing debouncing by hand. Consumers (external-change sync, Phase 2+) only need "something changed here, go re-check," so this is an acceptable simplification, not a workaround for a bug.
- Phase 1: `packages/core`'s `comments/ids.ts` needs `crypto.getRandomValues`, but core's tsconfig has neither "dom" nor "node" libs (by design, for platform-neutrality — SPEC.md §2.2). Added a 4-line ambient `declare const crypto` in `src/globals.d.ts` instead of pulling in a whole lib; both browser and Node 20+ provide the real global at runtime.
- Phase 1: `packages/core/package.json` takes `@marginalia/platform-node` as a **devDependency** (test-only) so `workspace.ts` can be integration-tested against real temp git repos without core depending on Node at runtime (the ESLint boundary rule only restricts `src/**`, not `test/**`). This makes the two packages a cyclic *workspace* dependency (pnpm warns, doesn't error) — harmless since it's dev-only and not part of either package's `tsconfig.json` project references, so `tsc -b` build order isn't actually circular.
- Phase 2: interpreted SPEC.md §9.2/§9.3's `for-each-ref`/`log` format strings that write `%1f`/`%1e` as shorthand for git's actual `%x1f`/`%x1e` (literal hex-byte field/record separators) — §9.5's own log format uses the correct `%x1f` spelling, so this is clearly the intent, not a different mechanism. Used `%x1f`/`%x1e` everywhere for consistency.
- Phase 2: `restoreToVersion`/`createSnapshot`/etc. write directly to disk via `SaveCommit` rather than "through the editor as a normal edit" (spec's literal wording for restore, §9.2) — that phrasing describes the *UI's* responsibility (so the restore is undoable in CodeMirror's history); the core-level function only needs to produce the correct commit. The real editor wiring for "restore via an undoable transaction" is left for whichever later phase first needs it interactively; `HistoryPanel.tsx` currently does a full reload after restore as a simple stand-in.
- Phase 3: comment creation (§8.2) uses a synchronous `window.prompt()` for the comment body instead of "focus a draft textarea in the Comments panel, submit with Cmd+Enter." The panel-focus version needs live draft-state coordination between `EditorPane` (owns the CodeMirror transaction) and `CommentsPanel` (owns the textarea) that's more plumbing than this pass justifies. Behavior matches otherwise: empty/cancelled input removes both tags and the thread.
- Phase 3: `EditorPane.tsx` exports a module-level `activeEditorView` ref so `CommentsPanel`'s re-anchor action can dispatch directly into the live CodeMirror view. Not idiomatic React (no context/provider), but it's a single cross-cutting concern and avoids threading a ref through props for one caller.
- Phase 3: comment bodies render through a small hand-rolled bold/italic/inline-code/newline converter (`CommentsPanel.tsx`'s `renderBody`), not the real `remark`/`unified` pipeline (that's specified for PDF export in §11.2, Phase 6, and pulling it into a React component here would mean async rendering + extra state for comment text that's usually one line). Revisit if Phase 6's pipeline turns out to share cleanly.
- Phase 3/general: no `Toolbar.tsx` yet (file name, Live/Source toggle, Comment button, Redline toggle, Snapshot, Export — SPEC.md §12). Comment creation is reachable via Cmd+Shift+M; toolbar buttons for the other actions will get built as their owning phases land (Redline in Phase 4, Export in Phase 6) rather than as empty placeholders now.
- Phase 4: initially built `redline`'s decoration recompute as a plain reactive `EditorView.decorations.compute([redlineField, "doc"], …)` (recomputes on every doc change), matching the "simplest option" instinct — but Spike B's own perf test caught that this makes typing in a 10,000-word doc take ~1000ms per keystroke with redline on, since `wordDiff` alone costs tens of ms and was being re-run synchronously on every single character. This is exactly the "150ms after doc changes, or immediately on toggle/baseline change" debounce spec actually specifies (§10.3) — rewrote `redline.ts` as a `ViewPlugin` with a real timer, restoring sub-2ms keystroke latency. Lesson: don't skip a spec'd debounce as a "simplification" without checking it against the perf benchmark that already exists for exactly this reason.
- Phase 4: the 10k-word/200-hunk benchmark (§13) is a single git-untracked-CPU-noise-sensitive number under `pnpm test`'s concurrent test files (versions.integration.test.ts spawns many `git` subprocesses; eslintBoundary.test.ts spins up ESLint) — isolated profiling shows a steady ~13-20ms cost, comfortably under the 50ms budget, but shared-machine contention pushed a single cold/median measurement over budget intermittently. Changed the test to warm up 3x then take the **minimum** of 8 samples (standard practice for measuring an algorithm's true cost under noise, not the noise itself) rather than loosening the 50ms budget.
