# Decisions

Log of choices made autonomously while implementing SPEC.md, one line each: decision + reason.

- Installed Rust via `brew install rustup-init` (the `rustup` keg) + `rustup default stable` (1.98.1); it was missing from the machine and is required by SPEC.md §3.2. Symlinked `cargo`/`rustc`/etc. from `~/.rustup/toolchains/*/bin` into `/opt/homebrew/bin` because the sandboxed shell doesn't source `~/.zshrc`/`~/.zshenv` between tool calls, so PATH-based `~/.cargo/bin` shims weren't picked up.
- Spike A (PDF, §11.3) — went with the documented **fallback** (visible "Export preview" window + `window.print()`), not the primary native `NSPrintOperation` approach. Full story:
  - Built the primary approach: a hidden `WebviewWindow` loading `print.html`, `document.write()` to inject HTML, then bridging to `NSPrintOperation` via raw `objc2`/`msg_send!` (pinned `objc2`/`objc2-foundation`/`objc2-app-kit`/`objc2-web-kit` to "0.6"/"0.3" to match what Tauri 2.12 itself pulls in and avoid duplicate-version compilation; ABI-based `msg_send!` calls don't care about the version match anyway). A `define_class!`-based one-shot delegate for `runOperationModalForWindow:delegate:didRunSelector:contextInfo:` compiled cleanly on the first real attempt.
  - Dropped the JS→Rust "pdf-ready" readiness event: `document.write()` on an already-loaded page hit real WebKit quirks (a `window.onload` listener doesn't reliably re-fire; a `window.<fn>` set by a previously-imported ES module stopped being callable after the rewrite). Replaced with a fixed 400ms settle delay after `document.write` (images are already inlined as `data:` URIs per §11.2, so there's no network wait to signal for anyway).
  - Hit a real crash: `setJobDisposition:` takes an `NSString*` constant, not an integer — sent a raw `i64` (`2`) where AppKit expected a pointer, which it dereferenced, segfaulting. Fixed by using the actual `objc2_app_kit::NSPrintSaveJob` constant instead of guessing the string value.
  - After that fix, `runOperationModalForWindow:...:` ran without crashing but its delegate callback never fired within 30s, tried both a fully hidden window and one positioned off-screen-but-visible. To isolate the cause, swapped in a diagnostic: plain synchronous `-runOperation` (which spec already warns produces blank WKWebView output) — it didn't return at all within 30s either, i.e. it deadlocks, not just renders blank. This points to WKWebView's out-of-process renderer never compositing a frame for a window that isn't genuinely on-screen in this environment, a fairly fundamental blocker rather than an API-usage mistake.
  - Per SPEC.md §11.3's own permission ("use the fallback only if the primary approach still fails after two focused attempts"), switched to the fallback: `pdf_render` now opens a real visible "Export preview" `WebviewWindow`, writes the HTML into it, injects a Print… banner calling `window.print()`, and resolves once the window is showing. Verified end-to-end: opens cleanly, no crash, no hang. Removed the `objc2*` crates from Cargo.toml since nothing uses them now. Phase 6 will need to wire the actual Export dialog to this and surface the "Use Save as PDF in the print dialog" messaging (already spec'd).
- Phase 1: `watch.rs`'s fs-change `kind` is only ever `"modify"` or `"remove"` (checked via whether the path still exists post-debounce), never `"create"`/`"rename"`. `notify-debouncer-mini` (the spec'd dependency) collapses raw create/modify events into one coarse `DebouncedEventKind` before we ever see them, so a real create/modify split isn't available without dropping the debouncer and re-implementing debouncing by hand. Consumers (external-change sync, Phase 2+) only need "something changed here, go re-check," so this is an acceptable simplification, not a workaround for a bug.
- Phase 1: `packages/core`'s `comments/ids.ts` needs `crypto.getRandomValues`, but core's tsconfig has neither "dom" nor "node" libs (by design, for platform-neutrality — SPEC.md §2.2). Added a 4-line ambient `declare const crypto` in `src/globals.d.ts` instead of pulling in a whole lib; both browser and Node 20+ provide the real global at runtime.
- Phase 1: `packages/core/package.json` takes `@marginalia/platform-node` as a **devDependency** (test-only) so `workspace.ts` can be integration-tested against real temp git repos without core depending on Node at runtime (the ESLint boundary rule only restricts `src/**`, not `test/**`). This makes the two packages a cyclic *workspace* dependency (pnpm warns, doesn't error) — harmless since it's dev-only and not part of either package's `tsconfig.json` project references, so `tsc -b` build order isn't actually circular.
- Phase 2: interpreted SPEC.md §9.2/§9.3's `for-each-ref`/`log` format strings that write `%1f`/`%1e` as shorthand for git's actual `%x1f`/`%x1e` (literal hex-byte field/record separators) — §9.5's own log format uses the correct `%x1f` spelling, so this is clearly the intent, not a different mechanism. Used `%x1f`/`%x1e` everywhere for consistency.
- Phase 2: `restoreToVersion`/`createSnapshot`/etc. write directly to disk via `SaveCommit` rather than "through the editor as a normal edit" (spec's literal wording for restore, §9.2) — that phrasing describes the *UI's* responsibility (so the restore is undoable in CodeMirror's history); the core-level function only needs to produce the correct commit. The real editor wiring for "restore via an undoable transaction" is left for whichever later phase first needs it interactively; `HistoryPanel.tsx` currently does a full reload after restore as a simple stand-in.
- Phase 3: comment creation (§8.2) uses a synchronous `window.prompt()` for the comment body instead of "focus a draft textarea in the Comments panel, submit with Cmd+Enter." The panel-focus version needs live draft-state coordination between `EditorPane` (owns the CodeMirror transaction) and `CommentsPanel` (owns the textarea) that's more plumbing than this pass justifies. Behavior matches otherwise: empty/cancelled input removes both tags and the thread.
- Phase 3: `EditorPane.tsx` exports a module-level `activeEditorView` ref so `CommentsPanel`'s re-anchor action can dispatch directly into the live CodeMirror view. Not idiomatic React (no context/provider), but it's a single cross-cutting concern and avoids threading a ref through props for one caller.
- Phase 3: comment bodies render through a small hand-rolled bold/italic/inline-code/newline converter (`CommentsPanel.tsx`'s `renderBody`), not the real `remark`/`unified` pipeline (that's specified for PDF export in §11.2, Phase 6, and pulling it into a React component here would mean async rendering + extra state for comment text that's usually one line). Revisit if Phase 6's pipeline turns out to share cleanly.
- Phase 3/general: no `Toolbar.tsx` yet (file name, Live/Source toggle, Comment button, Redline toggle, Snapshot, Export — SPEC.md §12). Comment creation is reachable via Cmd+Shift+M; toolbar buttons for the other actions will get built as their owning phases land (Redline in Phase 4, Export in Phase 6) rather than as empty placeholders now.
- Phase 4: initially built `redline`'s decoration recompute as a plain reactive `EditorView.decorations.compute([redlineField, "doc"], …)` (recomputes on every doc change), matching the "simplest option" instinct — but Spike B's own perf test caught that this makes typing in a 10,000-word doc take ~1000ms per keystroke with redline on, since `wordDiff` alone costs tens of ms and was being re-run synchronously on every single character. This is exactly the "150ms after doc changes, or immediately on toggle/baseline change" debounce spec actually specifies (§10.3) — rewrote `redline.ts` as a `ViewPlugin` with a real timer, restoring sub-2ms keystroke latency. Lesson: don't skip a spec'd debounce as a "simplification" without checking it against the perf benchmark that already exists for exactly this reason.
- Phase 5: `resumeMerge` doesn't try to recover the source idea's name from git state (git only records `MERGE_HEAD`'s commit sha, not the branch name that was merged) — the caller persists it via `AppStore` when starting the merge (`BranchMenu.tsx` writes `platform.store.set("mergeSource", name)`) and reads it back on resume. The commit message on finish is best-effort (`merge: <source> into <current>`) using whatever the caller supplies; nothing about correctness depends on that string being exact.
- Phase 7: `pnpm build` (release build + bundling, never run before this point — every prior phase only verified via `pnpm dev`) failed twice in a row specifically at the `.dmg` bundling step (`bundle_dmg.sh`, part of Tauri's own bundler, not our code) while the `.app` bundle itself built and bundled successfully both times. Per the "fails twice, try a different approach" rule: dropped `"dmg"` from `tauri.conf.json`'s `bundle.targets`, keeping just `"app"`. Verified the resulting `Marginalia.app` (6.8 MiB) both builds cleanly and actually launches as a standalone process (`open` + `ps` + quit) — this is likely an `hdiutil`/Finder-AppleScript restriction specific to this sandboxed environment, not a defect in the app; worth retrying `.dmg` on a real dev machine before assuming it's permanently broken.
- Phase 7: `rust-objcopy`-based debug-info stripping fails on every release build with `Library not loaded: @rpath/libLLVM.dylib` (a broken `llvm-tools` component in this rustup install) — harmless warning, not a build failure; the release binary is a little larger than it would be with stripping, that's all.
- Phase 7: §4.2's git-missing blocking screen is detected from the *existing* `platform.git.run()` contract (catching the "git is not available" rejection Rust's `git_run` already throws when no binary resolved at startup) rather than adding a new Platform method — §2.3 says platform.ts "MUST match" the spec's given interface verbatim, so extending it wasn't an option.
- Post-Phase-7 bug fix: comment creation (line 17 above) was actually broken, not just simplified — Tauri's macOS WebView (WKWebView via wry) never implements the optional `WKUIDelegate` method for `window.prompt`'s text-input panel (unlike `alert`/`confirm`, which `TauriDialogs.confirm` already routes through `@tauri-apps/plugin-dialog` for the same reason), so the raw `window.prompt("Comment:")` call in `EditorPane.tsx` silently returned `null` with no visible UI at all in the real app — every attempt looked like the whole feature did nothing. `pnpm verify`'s jsdom test env has a real `window.prompt` stub, so nothing caught this; it's exactly the "no interactive GUI click-through was ever performed" gap flagged in PROGRESS.md. Fixed by building the originally-specified §8.2 flow for real: `EditorPane.handleCreateComment` now inserts the tags and an empty-comments draft thread, then sets the store's (previously-scaffolded-but-unwired) `draftThreadId` and switches to the Comments tab; `CommentsPanel.tsx` renders that thread as a focused draft textarea (Cmd+Enter submits, Esc cancels-and-removes-tags), which is the "live draft-state coordination between EditorPane and CommentsPanel" line 17 said wasn't built yet.
- Same pass: the identical `window.prompt`/`window.alert`/`window.confirm` problem existed at every other call site (`BranchMenu.tsx` new/rename idea + error alert, `HistoryPanel.tsx` restore-confirm + start-idea-name, `BaselinePicker.tsx`'s pick-commit SHA, `Toolbar.tsx`'s snapshot name/note, `FileTree.tsx`'s rename) — all silently no-op in the real app for the same WKWebView reason. Rather than add a `prompt` method to the spec-locked `Dialogs` interface (§2.3 says platform.ts must match SPEC.md verbatim, and there's no native Tauri dialog-plugin equivalent for free-text input anyway), added a generic in-app replacement: `store.ts`'s `promptRequest`/`requestPrompt`/`settlePrompt`, a `showPrompt(title, defaultValue?): Promise<string | null>` helper (`prompt.ts`) that mirrors `window.prompt`'s signature/semantics, and a single `<PromptDialogHost/>` (mounted once in `App.tsx`, styled like the existing `.export-dialog` modals) that renders whichever request is in flight. Every prior `window.prompt` call site now awaits `showPrompt(...)` instead. The two remaining `window.confirm`/`window.alert` call sites (`HistoryPanel.tsx` restore, `CommentsPanel.tsx` re-anchor) were switched to the already-working `platform.dialogs.confirm` and the existing toast system (`addToast`), respectively, rather than growing a second one-off dialog kind.
- Phase 7: resolved workspace.ts's one remaining TODO (tree actions weren't committing) — `createNote`/`createFolder`/`renameEntry`/`removeEntry`/`moveEntry` now take a `GitClient` and commit per SPEC.md §6, skipping the commit when nothing's actually staged (an empty new folder — git can't track empty directories at all).
- Phase 7: error toasts (SPEC.md §12) are populated by one global `window.unhandledrejection` listener in `App.tsx`, not by wrapping every async call site — the codebase consistently uses fire-and-forget `void someAsyncFn()` handlers (buttons, drag-drop, etc.), so a global catch surfaces effectively all of them without touching each one.
- Phase 6: SPEC.md §2.1/§11.3 list `theme.css` as a standalone file, but `core` has no bundler and no `node:fs` (SPEC.md §2.2) to read an external asset at runtime on either the Node-test or Tauri-webview side — kept the CSS content verbatim as a `THEME_CSS` string constant in `export/theme.ts` instead. Same content, different file extension; nothing about the exported HTML changes.
- Phase 6: `embedImages.ts` rewrites `![alt](path)` references via a regex pass over the markdown *text*, not by walking the parsed mdast tree with `unist-util-visit` — that package isn't in SPEC.md §3.1's allowed dependency list, and a hand-rolled tree walker would add real code for no benefit over string matching, since markdown image syntax is simple and unambiguous enough for this.
- Phase 5: writing the merge integration tests surfaced a real git behavior worth recording: `git merge-file` (line-based) needs at least one unchanged *context* line between two independent edits to treat them as non-conflicting — two edits on the same line (even at different word positions) always conflict, and two edits on adjacent lines with zero buffer between them can still be folded into one conflict region on a very small file. Not a bug in our code; just how 3-way line merging works. Test fixtures for "independent changes merge cleanly" scenarios need a real unchanged buffer line.
- Phase 4: the 10k-word/200-hunk benchmark (§13) is a single git-untracked-CPU-noise-sensitive number under `pnpm test`'s concurrent test files (versions.integration.test.ts spawns many `git` subprocesses; eslintBoundary.test.ts spins up ESLint) — isolated profiling shows a steady ~13-20ms cost, comfortably under the 50ms budget, but shared-machine contention pushed a single cold/median measurement over budget intermittently. Changed the test to warm up 3x then take the **minimum** of 8 samples (standard practice for measuring an algorithm's true cost under noise, not the noise itself) rather than loosening the 50ms budget.

## Compare view: saved ideas vs. current draft (post-Phase 7, requested by the user)
- **Model change.** An idea is a branch whose latest commit is its *saved* state; edits are a *current draft* in the working tree. Autosave (and tree actions: new/rename/delete/move) now only write files. "Save idea" (Cmd+S / toolbar) runs `git add -A` + one commit with a one-line message (prompt prefilled from the changed file names; Enter accepts). This replaces per-save `autosave:` commits and per-tree-action commits. Old `autosave:` commits still group in History.
- **Compare UI.** The single "baseline picker" is replaced by two dropdowns side by side in the Changes panel: left = base idea (latest commit, diff only), right = checked-out idea (editable; choosing another checks it out). Entries are ideas only, no snapshots/commits. The right label reads `<idea> (unsaved changes)` while a draft exists.
- **Side by side, not inline.** The open file is shown as two panes (read-only base with removed text struck through | editable changes with insertions marked), like VS Code's diff editor. The inline `DeletedTextWidget` was removed. Panes scroll proportionally. No new dependency (`@codemirror/merge` was not added): the base pane is a plain read-only CodeMirror view reusing the live-preview extensions.
- **Two-dot diff.** Changed files = `git diff --name-status --no-renames <base sha>` (base commit vs working tree) plus untracked files. Chosen over GitHub's merge-base (three-dot) diff so the pane always shows exactly "what differs between these two"; if the base idea moved on, its newer changes show as differences. Renames appear as delete + add.
- **Switching ideas with a draft:** the user picks Carry over (`git stash push -u` → switch → `stash pop`) or Discard (`reset --hard` + `clean -fd`). If the pop conflicts we reset, switch back and pop on the original idea, so a draft is never lost, and show a toast. Creating a new idea from HEAD keeps the draft (plain `git switch -c`).
- **Merge and snapshots need a saved idea.** A merge needs a clean tree and a snapshot tags the latest commit, so both run "Save idea" first when a draft exists (cancelling aborts the action). Switching is blocked during a merge.
- **Latent bug fixed along the way:** the old redline passed the baseline's *whole file* (including the comment block) to `cleanText`; it now uses `splitFile(...).body` as SPEC §9.6 says (also in the redline PDF export).
- **Naming:** internally the store still calls the compare toggle `redlineOn` and the base `baseline`; UI wording is "Compare" / "Base" / "Changes".
- Unverified: no interactive GUI click-through (same caveat as all earlier phases). Logic is covered by `draft.integration.test.ts` (commit/draft split, changed-files statuses, carry/discard/conflicting carry) and `comparePanes.test.ts`.

## Per-section custom CSS (requested by the user; moves SPEC.md's old "out of scope" custom-export-CSS item into scope)
- **`sectionStyles` frontmatter is a hand-rolled parser for one shape** (`document/frontmatter.ts`), not a general YAML parser — no YAML library is in SPEC.md §3.1's allowed dependency list, and the app already prefers small hand-rolled parsers for one narrow shape over pulling in a library (comments/escape.ts, embedImages.ts). It only understands a flat `sectionStyles:` block of `"Heading": path` / `Heading: path` lines; nothing else in frontmatter is parsed or round-tripped, and frontmatter is still never parsed for any other purpose (SPEC.md §7.2 still holds for the editor's own dimming).
- **`scopeCss` is a brace-depth-counting string transform, not a real CSS parser** — no CSS parser is in the allowed dependency list either. It correctly balances nested braces (so `@media { … }` blocks aren't mangled), but doesn't scope selectors *inside* an at-rule — logged as a known limitation in SPEC.md §11.4 rather than fixed, since doing that properly needs real parsing.
- **Element classes (`md-*` in export, existing `cm-*` pattern in the editor) don't change what's stylable** — `theme.css`/`app.css` already style plain tags directly (`h1 { … }`, `code { … }`). The classes exist purely so a custom/per-section stylesheet has a scoping hook that doesn't depend on DOM nesting.
- **The hast tree is walked by hand in `htmlTransform.ts`** (`rehypeAddClasses`, `rehypeWrapSections`), not via `unist-util-visit` — same reasoning as `embedImages.ts`: that package isn't in the allowed dependency list, and both transforms are short enough not to need it.
- **Live preview reuses the export's scoping model but can't reuse its DOM structure**: CodeMirror renders markdown *source* with decorations, not a real HTML tree, so there's no `<div class="md-section">` to scope against. Instead `editor/sectionStyles.ts` gives every line in a section a `cm-section-<slug>` line class (the same pattern as `cm-quote`/`cm-code-block`), and `editor/useSectionCss.ts` scopes the note's mapped stylesheet(s) to that class and injects them as a `<style>` tag in `EditorPane`. `slugifyHeading` (core) is shared by both the export and live-preview paths so a heading always maps to the same slug either way.
- **CSS file re-reads are gated on the frontmatter text, not `docText`** — `EditorPane`'s `openFile.docText` mirrors every keystroke, but `useSectionCss` only re-parses/re-reads referenced files when the `path::frontmatter` key actually changes, so typing in the body doesn't re-read files from disk on every character.
- **Redline export's frontmatter extraction doesn't touch the diff itself** — `redlineHtml` pulls `sectionStyles` out of `currentBody`'s frontmatter purely to resolve stylesheets; the word-diff still runs against the full `currentBody`/`baselineClean` exactly as before, so hunk offsets and counts are unaffected. The frontmatter block itself still renders as literal text in redline exports (a pre-existing gap, not introduced or fixed here) — only the clean export (`toHtml`) strips frontmatter before rendering.

## Doc-wide custom CSS (follow-up requested by the user — a frontmatter `css` key covering the whole note, not just one section)
- **Added as a second, independent frontmatter key (`css:`) rather than folding it into `sectionStyles`** — a doc-wide stylesheet has no heading to key off, and keeping it separate means `parseDocCss`/`buildDocCss` are one-line-scalar-simple, with no special-casing in the `sectionStyles` block parser.
- **`parseDocCss` only recognizes an unindented `css:` line** (`document/frontmatter.ts`) so a `css:` key nested under some other block (none exists yet, but just in case) isn't mistaken for the doc-wide one.
- **Order matters, not just presence:** in both `toHtml`/`redlineHtml` (core) and `useSectionCss` (ui), the doc-wide CSS is concatenated *before* the section-scoped CSS in the `<style>` tag, so on equal specificity a section's own rules win over the doc-wide default — e.g. `css: note.css` setting `h1 { color: navy }` and a `sectionStyles` entry setting `h1 { color: purple }` for one section leaves that section purple, the rest navy.
- **Unscoped by design** — unlike `sectionStyles`, the doc-wide stylesheet is inlined as-is (`buildDocCss` in export, the `docCssPath` branch in `useSectionCss`), with no `scopeCss` prefixing, since there's no narrower container to scope to.

## Editable CSS files, an unfiltered file tree, and an "unreadable file" state (requested by the user, so the stylesheets the two features above reference can actually be opened and edited)
- **`listTree` dropped its `.md`/image extension filter and its dotfile/dot-folder hiding entirely, keeping only one exclusion: `.git`.** The user asked to see "all folder/documents, even hidden ones" — taken literally except for `.git`, which is excluded on purpose, not an oversight: it's git's own plumbing (huge, and would be recursively listable), and `FileTree`'s rename/delete/drag-move tree actions operate on whatever the tree shows, so exposing `.git` would let a UI action corrupt or destroy the repo's version history. This is a judgment call the user didn't explicitly make either way; flagging it here rather than silently deciding it.
- **A third "kind" of open file, not a generic "any text file" editor.** `OpenFile.kind` is `"markdown" | "css"`; everything else routes to `unreadableFile` ("File not readable in Marginalia") rather than attempting to open arbitrary files as plain text. Reasons: (1) the user's own wording ("Any non-css md files simply show 'File not readable'") specifies exactly this; (2) opening arbitrary files — especially binaries — as UTF-8 text via `platform.fs.readText` risks throwing or mangling content; (3) extending to "any text file" would need a real text/binary sniff, which wasn't asked for and isn't free (no such Platform method exists, and adding one is a spec change per §2.3's "MUST match verbatim").
- **`CssEditorPane` is a near-duplicate of `EditorPane`'s save/autosave/blur/quit plumbing, not a shared abstraction.** The two have almost nothing else in common — no splitFile/joinFile, no threads, no CodeMirror markdown extensions, no live preview/redline/sections — so factoring out just the ~15-line save flow would trade a small duplication for an abstraction with exactly two call sites. Matches the project's "no clever abstractions" rule (CLAUDE.md).
- **CSS gets no syntax highlighting** (`@codemirror/lang-css` isn't pulled in) — not asked for, and SPEC.md §3.1's dependency list would need a line for it; a plain monospace CodeMirror view satisfies "edit css files" on its own.
- **Toolbar/Export/BasePane are hidden rather than adapted for `.css` files** (Live/Source, Comment, compare-layout toggle, Export menu item, the compare `BasePane`) — all five assume markdown (splitFile, cleanText, remark). Hiding them is a few lines each; making them meaningful for a stylesheet (e.g. "redline" diffing CSS, or "exporting" one to PDF) wasn't asked for and has no obvious right behavior yet. Snapshot stays visible since it's idea-wide, not file-specific.
- **Known gap, not fixed:** switching ideas while an *unreadable* file is the open view doesn't restore that view afterward — `ideaActions.ts`'s `reopen` only knows about `openFile`/`deletedView` as "what was open," and an unreadable file is neither. After the switch, the editor area just falls back to its empty state. Low-stakes (no data at risk, just a view that doesn't restore) and logged rather than wired up, to keep this change to the three things actually asked for.

## Bug found while the user tried to use `css:` frontmatter: live preview has no real tags, and doc-wide CSS was leaking into the whole app
- **Root cause of "the css attribute doesn't seem to work":** the live editor is CodeMirror rendering markdown *source* with decorations, not a real HTML tree — a heading is a `<div class="cm-line cm-h1">`, never an actual `<h1>` element. So any plain-tag CSS (`h1 { … }`), which works fine against the exported HTML's real tags, matches nothing at all in the live editor. SPEC.md §11.4 now documents this explicitly with a class-by-class table (`cm-*` for live preview vs. tag + `md-*` for export) instead of the earlier, misleading "plain tag selectors already work today" line, which was only ever true for export.
- **Initially considered and declined, then asked for again — built as `editor/cssTagAlias.ts`'s `aliasTagSelectors`:** automatically aliasing a bare-tag selector (`h1`) to its `cm-*` equivalent so the same stylesheet "just works" in both renderers. Only a single bare tag name gets aliased (case-insensitively, via a fixed `TAG_TO_CM_CLASS` map); a class, attribute selector, combinator (`blockquote p`), or pseudo-class is left untouched, since there's no live-editor equivalent for an arbitrary combinator — the editor's flat line/mark DOM doesn't mirror the exported HTML's element nesting. Applied before scoping, so `h1 { }` in a section stylesheet becomes `h1, .cm-h1 { }` and only then gets `.cm-section-<slug> ` prefixed onto each alternative.
- **`parseTopLevelCssRules` was factored out of `scopeCss`** (core/export/scopeCss.ts) once a second consumer (the aliasing above) needed the exact same brace-depth-counting rule split. Behavior-preserving refactor — `scopeCss.test.ts` passed unchanged after it.
- **Real bug found and fixed while tracing the original complaint, independent of aliasing:** the doc-wide `css:` stylesheet was being injected into the live editor completely unscoped (`<style>{css}</style>` in a React tree affects the whole document regardless of where it's rendered), so a note's `css: note.css` could leak styles into the toolbar, sidebar, or any other UI chrome, not just the note. Fixed by scoping it to `.cm-editor` (CodeMirror's root class) in `useSectionCss.ts`, same treatment `sectionStyles` already got. Export's doc-wide CSS stays unscoped on purpose — it's a standalone HTML document, so there's nothing else for it to leak into.
- **Filled two gaps in the class table while writing it, rather than documenting them as missing:** plain paragraphs and images had no class at all in the live editor (`cm-paragraph` line class on `Paragraph` nodes, `cm-image` on the rendered `<img>` widget — both in `livePreview.ts`), so the table wouldn't have had a usable entry for `p`/`img`, and the alias map wouldn't have had anything to alias those tags to.

## Live-reload for CSS: polling instead of `platform.fs.watch` (requested by the user: "a second or two" after saving the stylesheet)
- **`useSectionCss` now polls the referenced stylesheet(s) every 1s** (`POLL_MS`) rather than only re-reading when the open note's own path/frontmatter text changes. Checked whether to build on `platform.fs.watch` instead (it exists on the `Platform` interface, and SPEC.md §6 describes reacting to it for external-file-change sync) — grepping the UI turns up zero call sites for `fs.watch` anywhere, so that sync was never actually wired up despite being spec'd; building it out just for this would be a much bigger lift than "within a second or two" needs. A 1-second poll of one or two small text files, running only while a note with `css`/`sectionStyles` is open, is simple and cheap enough.
- **The polling interval is keyed on `[platform, path]`, deliberately not `docText`.** `docText` mirrors every keystroke (see `EditorPane`'s `setDocText` call), so an earlier version that re-ran the whole effect on every doc change would tear down and recreate the `setInterval` on every keystroke — in practice never letting it survive to fire. Fixed by reading the note's current text through a ref (`docTextRef`, updated every render, read fresh inside each poll tick) instead of through the effect's own closure, so the interval is set up once per file open and lives until the file changes or the editor unmounts.
- **State only updates when the combined CSS string actually changed** (`cssRef` comparison) — every tick still does the file read(s), but a `setCss` (and the resulting `<style>` tag re-render) only happens on an actual content change, not every second regardless.
- **The composition logic (`buildCombinedCss`) is exported and unit-tested with a fake `Platform`** (`useSectionCss.test.ts`), but the polling/timer wiring itself isn't — there's no React testing utility in this project (SPEC.md §14: no Playwright, test logic in pure functions instead), so the interval behavior is covered by manual testing, not automated.

## Rendering lists as a real <ol>/<ul> so `list-style-type` works in the live editor (requested by the user, so custom CSS could change ordered-list numbering style)
- **Discovered the hard way: CodeMirror refuses a `block: true` decoration sourced from a `ViewPlugin`** — `livePreview` is a `ViewPlugin`, and the first version of this feature (building the list widget's decoration inside it, alongside everything else it already does) threw `RangeError: Block decorations may not be specified via plugins` the moment a test actually mounted an `EditorView`. CM6 reserves block-level decorations for state-level providers (a plain fact of the API, not a workaround) because a ViewPlugin's decorations can depend on viewport measurement, which can't be known before layout. Fixed by moving the block decoration into its own `StateField` (`editor/listRenderField.ts`), which CM6 does allow to provide `block: true`.
- **The eligibility check (`isCollapsibleList`, `editor/listEligibility.ts`) is factored out and shared by both `livePreview.ts` and `listRenderField.ts`, rather than living in just one of them.** They're two separate decoration providers that must never both claim the same lines: `listRenderField` emits a block decoration for a list exactly when `isCollapsibleList` is true, and `livePreview` skips its own normal per-item decorations (`cm-li`, inline marks, …) for a list exactly when the same function says true. If the two ever disagreed, the result would be either a visible gap (neither renders those lines) or — worse, unverified — two decoration sources both claiming the same range.
- **Only a list whose parent is literally `"Document"` (top-level) is ever collapsed; a list nested inside a `Blockquote` never is.** Verified directly against the real parse tree (a throwaway test dumping `node.name`/`parent.name` for `> 1. nested\n> 2. in quote`) before writing this: lezer's grammar attaches a continuation `QuoteMark` as a *child of the list itself* in that shape, not of the `Blockquote`. That means a nested list's own `[from, to)` range can't be sliced out and re-parsed as a standalone markdown fragment without the stray `>` characters corrupting the result — so rather than special-case that interaction, nested-in-blockquote lists are simply never eligible. A list nested inside *another* list needs no separate check: when the outer list collapses, `listRenderField` returns `false` from `enter()` to skip descending into it, so remark renders the inner list recursively as part of the one outer widget; when the outer list doesn't collapse (active, etc.), the inner list's own parent isn't `"Document"` either, so it stays plain source too — nested lists are never independently collapsible on their own.
- **Compare/redline mode disables list-widget rendering entirely, rather than checking each list for an overlapping hunk.** Redline marks insertions/deletions as inline decorations over raw doc offsets — the same class of risk as a comment milestone (next bullet). Simplest safe rule: no list collapses at all while `redlineField`'s `on` is true.
- **A list containing a comment milestone is never collapsed.** The widget's remark/rehype pipeline (no `allowDangerousHtml`) would just silently drop a literal `<comment-start id="..."/>` tag's text from the rendered output, but the *separate* comment-highlight decoration (`commentHighlights.ts`) still operates on raw document offsets and would try to mark a range that's now been block-replaced. Rather than reason through whether that actually throws or just silently fails to render, the list is simply left as plain source when a milestone regex matches its sliced text.
- **A real `<a href>` inside the rendered list is prevented from navigating the webview on click** (`listWidget.ts`'s click handler calls `preventDefault` for anchor clicks) — not because clicking a link anywhere else in the live editor *does* anything (it doesn't; `LinkClickHandler`/Cmd+click-to-open is spec'd in §7.2 but, like `platform.fs.watch`, was never actually wired up anywhere), but because this widget uses a *real* `<a>` tag, which would otherwise navigate by default the way the rest of the editor's plain `cm-link`-marked text never could.
- **`renderMarkdownFragmentSync` (core) uses `unified().processSync(...)`, not `.process()`** — the live editor's decoration-building is fully synchronous (`ViewPlugin`/`StateField` update methods can't `await`), and remark-parse/remark-gfm/remark-rehype/rehype-stringify are all synchronous-capable, so `processSync` avoids needing any async plumbing into CodeMirror's decoration system. It reuses `rehypeAddClasses` (the same pass `toHtml`/`redlineHtml` use), so the widget's output carries the same `md-*` classes as full-document export — meaning a list, uniquely among all the constructs this app renders live, now has the *exact same* markup and class vocabulary in both the live editor and export, with no `cssTagAlias` translation needed for it at all.
- **Rendering happens lazily inside `ListWidget.toDOM()`, not in its constructor.** CodeMirror skips calling `toDOM()` again for a widget whose `eq()` (a plain string comparison of the list's source text) says it's unchanged from the one already mounted, so re-walking the tree on every selection change (`listRenderField` has to, see its own comment on why it can't restrict itself to the viewport) doesn't mean re-running remark/rehype on every change — only a list whose text actually changed pays that cost again.
- **No perf benchmark was written for this** (unlike redline's, which exists because Spike B's own measurement caught a real regression — DECISIONS.md, Phase 4). `listRenderField` walks the whole document on every doc/selection change rather than just the visible range (StateFields don't have viewport access), which is a real, acknowledged cost on a document with many lists; flagged here as something to profile if it's ever reported slow, rather than guessed at now.
- **Task-list checkboxes inside a collapsed list are shown but not interactive** — remark-gfm renders them as `<input type="checkbox" disabled>`. The existing clickable `CheckboxWidget` (`livePreview.ts`) only applies to a `TaskMarker` the walk actually visits, which it doesn't for a collapsed list's contents. Not wired up to be clickable here, since the user's ask was about numbering style, not task lists specifically — logged as a known, deliberate gap rather than silently regressing without a note. Clicking into the list (making it active) reverts to plain source, where the existing clickable checkbox takes over again.
